# Ñkyel Database Architecture

This document describes the foundational database architecture for the Ñkyel agentic platform. 
The system uses Neon Serverless PostgreSQL as the transactional source of truth, managed via Drizzle ORM.

## Core Tenets

1. **Strict Persistence:** All critical business data, state, missions, conversations, configurations, and artifacts are strictly persisted to Neon PostgreSQL. `localStorage` is completely forbidden for these entities.
2. **Immutability & Auditability:** Temporal data is captured meticulously. The `mission_events` table acts as an append-only event spine. Audit logs track user and agent actions across the system.
3. **Multi-Tenancy:** The data model is strictly multi-tenant. The `workspaces` table sits at the top of the hierarchy, and almost every domain table includes a `workspace_id` foreign key.
4. **Resiliency:** Foreign keys are heavily utilized to maintain referential integrity. Extensive use of cascading deletes ensures clean-up of orphaned resources, while restricted deletes protect critical entities like users.

## Domain Groups

### 1. Identity & Tenancy
- **`users`**: Represents individuals (via Clerk `clerk_user_id`).
- **`workspaces`**: The tenant boundary (e.g., Personal, Team, Business).
- **`workspace_members`**: Manages RBAC and access mapping between Users and Workspaces.
- **`user_settings` & `workspace_settings`**: Configurations for interface presentation and tenant policies.

### 2. Core & Projects
- **`projects`**: High-level organizational units for segregating work within a Workspace.

### 3. Conversations & Messages
- **`conversations`**: Holds the chat sessions (either standard chat or mission-oriented chat).
- **`messages`**: Ordered chat fragments utilizing a monotonic `sequence` for ordering.

### 4. Intelligence & Execution (The "Mission" Domain)
- **`missions`**: Represents a complex, agentic goal or workflow.
- **`runs`**: Executions of a mission.
- **`mission_events`**: The central nervous system logging every step (tool calls, thoughts, checkpoints).
- **`checkpoints`**: Deterministic state captures allowing for pause, resume, and rewind capabilities.
- **`tasks`**: Granular steps orchestrated by the agents.
- **`simulations` & `predictions`**: Pre-flight analysis and outcome projections.

### 5. WorkGraph
- **`workgraph_nodes` & `workgraph_edges`**: Represents complex relationships, pipelines, and artifacts as a directed graph.

### 6. Evidence & Decisions
- **`sources` & `evidence`**: Tracks citations and factual provenance.
- **`decisions`, `approval_requests`, `approval_decisions`**: Manages autonomous decisions and required human-in-the-loop approvals.

### 7. Agents, Tools & MCP
- **`agents` & `agent_versions`**: The cognitive workers. Versions are immutable.
- **`tools` & `tool_executions`**: The functional capabilities invoked by agents.
- **`connections`, `mcp_servers`, `mcp_tools`**: External integrations and Model Context Protocol interfaces.

### 8. Artifacts
- **`artifacts` & `artifact_versions`**: Documents, images, code files, or dynamic content generated by the agents or uploaded by users. Binaries reside in R2, but transactional metadata and versioning are managed here.

### 9. Memory
- **`memories`**: Textual representations linking directly to Qdrant vector database IDs (`qdrant_point_id`) for RAG operations.

### 10. Security, Sharing & Telemetry
- **`share_links`**: Granular resource sharing capabilities.
- **`usage_events` & `quota_counters`**: Billing, rate limiting, and analytics.
- **`audit_logs` & `feedback`**: System monitoring and user feedback loops.

## Database Constraints and Types
- **UUIDs**: Native `uuid` for all Primary Keys (generated via `uuid_generate_v4()`).
- **Timestamps**: Uses `TIMESTAMPTZ` (`timestamp with time zone`) for accurate global logging.
- **JSONB**: Used for `metadata`, `safe_diagnostics`, and dynamic configurations to ensure extensibility without constant schema alterations.

## Data Migration & Evolutions
Any future schema changes MUST be done via declarative Drizzle changes in `schema.ts`, followed by generating migrations with `npx drizzle-kit generate` and applying them with `npx drizzle-kit migrate` or `drizzle-kit push`.
